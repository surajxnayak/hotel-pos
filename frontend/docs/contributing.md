# Contributing

## Coding conventions

- **JavaScript, not TypeScript.** DTO shapes live in `API_REFERENCE.md` — reference it, don't reinvent it in `.d.ts` files.
- **Functional components + hooks.** No class components.
- **State stays local unless it can't.** `localStorage` is fine for auth/session persistence; everything else is `useState`/`useReducer` inside the owning view.
- **REST is the source of truth** (see [data-flow.md](./data-flow.md)). Never build UI state that the backend can't reconstruct.
- **No optimistic UI** except where explicitly justified (see the `justRequestedBill` comment in `OrderSession.js`).
- **Every endpoint helper lives in `lib/api.js`.** Don't `axios.get(...)` inline from a component.

## File layout

- Reusable UI → `components/`.
- Route-level screens → `views/`.
- REST helpers → `lib/api.js`.
- WebSocket factory → `lib/ws.js`.
- localStorage helpers → `lib/session.js`.

## `data-testid` policy

Every interactive element and every element showing critical/user-facing info must have a `data-testid`. Rules:

- Kebab-case, describes function, not style.
- Unique per screen (no duplicates within a single mounted page).
- Standard prefixes already in use: `menu-item-{id}`, `add-to-cart-btn-{id}`, `cart-item-{id}`, `qty-{id}`, `submit-order-btn`, `confirm-order-{orderId}`, `serve-item-{itemId}`, `picker-item-{id}`, `picker-draft-{key}`, `customization-modal`, `customization-option-{id}`, `waiter-tables-page`, `kitchen-queue-view`, `staff-refresh-btn`, `operate-mode-slider`, `operate-{role}`.
- New feature? Extend the pattern.

## When adding a screen

1. Register the route in `App.js` (with `ProtectedStaffRoute` if it's staff-facing).
2. Create the view in `views/` — return an outer container with `<StaffShell>` or `<AdminShell>` as appropriate.
3. Fetch data with a REST call in `useEffect`; add `createStompClient` if the backend broadcasts on a relevant topic.
4. Reconcile on WS reconnect + `visibilitychange` + `online` — see the pattern in [data-flow.md](./data-flow.md#the-pattern).
5. Add `data-testid`s to every interactive element.

## When adding a new endpoint

1. Add a helper to `lib/api.js` in the right section (customer / waiter / kitchen / cashier / admin).
2. Return `.then((r) => r.data)` so callers see the body directly.
3. Sanitize the payload if the backend rejects extra fields.
4. If the endpoint is PIN-gated, the helper takes `pin` as its first meaningful argument and the caller shows `<PinModal />` to collect it.
5. Update the API-integration doc.

## Editing existing components

- **Reuse before duplicating.** `OrderList`, `CustomizationModal`, `SelectedOptions`, `DietaryBadge`, `StatusBadge`, `TableGrid`, `DetailPanel`, `PinModal` are all shared for a reason — extend them with props before forking.
- Use `search_replace`-style targeted edits rather than rewriting files whole.

## Testing during development

- Every screen has a floating **Debug** button (bottom-right). Filter by `api` / `ws` / `error`.
- API-level testing: use `curl` against `REACT_APP_API_BASE_URL` — the app doesn't wrap anything mysterious.

## Commit hygiene

- One logical change per commit.
- The API reference (`API_REFERENCE.md`) is generated by the backend team. Do not hand-edit it; if you find a discrepancy, flag it to them and only fix the frontend to match reality after the doc is updated.

## PR checklist

- [ ] New endpoints have a helper in `lib/api.js`.
- [ ] New interactive elements have `data-testid`s.
- [ ] Every new `useEffect` that subscribes to a topic also reconciles on reconnect / visibility / online.
- [ ] No `notes` field is sent by the customer flow (staff-only per API contract).
- [ ] Every catch block surfaces the backend `e.message` via a toast unless silence is explicitly justified.
- [ ] Docs updated (this folder) if the change is user-facing or architectural.
